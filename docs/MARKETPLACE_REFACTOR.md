# Marketplace refactor — shared catalog + per-seller offers

## Why

Today every seller upload creates its own `Product` record with its own slug.
When two sellers offer the same physical product (e.g. "Axor Apex Helmet"),
the second one becomes `/product/axor-apex-helmet-2`. This splits SEO,
fragments inventory, and shows duplicate cards in search/category listings.

## Target architecture

Two models:

**`CatalogProduct`** — one record per real-world product. Brand-level info.

```
{
  _id, brand, category, bike?,
  name, slug,            // canonical, never collides
  description, images[], sizes[],
  mrp,                   // suggested retail price (catalog-level)
  rating, reviewsCount,  // aggregated across all offers
  status: 'active' | 'archived',
  seoTitle, seoDescription, ogImage,
  createdAt, updatedAt,
}
```

**`SellerOffer`** — one record per seller per product. Seller-specific
pricing + stock + fulfillment. This is the existing `Product` after
extracting brand-level fields up.

```
{
  _id, catalog,          // → CatalogProduct
  seller,                // → User
  price, mrp?,           // mrp optional override
  stock, sku,
  condition: 'new',      // future: 'refurbished' | 'used'
  status: 'active' | 'paused',
  createdAt, updatedAt,
}
```

Defaults adopted (no longer up for discussion):
- Cart auto-picks the **lowest-price, in-stock** offer. Customer can switch.
- Reviews live on `CatalogProduct` (aggregated across offers).
- Returns / exchanges stay scoped to the seller the customer bought from.
- For now `SellerOffer` only carries price + stock + sku. No condition /
  variant fields. Easy to add later.

## Phased milestones (ship one at a time)

### M1 — Data model + non-destructive migration  ✅ shipped
- `CatalogProduct` model + schema
- Add `catalog: ObjectId` field to existing `Product` (nullable for now)
- Migration script:
  - For each unique (brand, normalized-name) pair → create one CatalogProduct
  - Copy brand-level fields up (name, description, images, sizes, mrp, category, bike)
  - Slug = canonical slug of name (no `-2` suffixes; first seller wins ties)
  - Set `product.catalog = catalogProduct._id` on every linked Product
- New endpoints:
  - `GET /api/catalog/:slug` — returns catalog + array of active offers
  - `GET /api/catalog?…filters` — listing, dedupes by catalog
- No frontend changes; existing endpoints keep working
- Verification: `db.catalogproducts.count() <= db.products.count()` (it should be strictly less for products with duplicate brand+name)

### M2 — Customer-side reads  ✅ shipped
- ProductDetailPage rewrites to read from `/api/catalog/:slug`
- Adds "Available from N sellers" widget below price, lists each seller
  with their price + ETA. Customer selects which seller to buy from
  (defaults to lowest-price in-stock).
- CategoryPage product cards dedupe by catalog
- Reviews fetched per-catalog (need backend aggregation)
- 301 redirects from old `axor-apex-helmet-2` style slugs to the catalog slug

**Shipped (M2):** ProductDetailPage + its SSR/JSON-LD read `/api/catalog/:slug`;
"Available from N sellers" widget (price + stock + store, defaults to
lowest-price in-stock; ETA via the per-seller delivery checker). CategoryPage +
its SSR + the related-products rail read the deduped `/api/catalog` listing
(now also returns `inStockOffersCount`; `lowestPrice` prefers in-stock).
Per-catalog reviews via `GET /api/catalog/:slug/reviews`, with Review
save/delete hooks recomputing `CatalogProduct.rating/reviewsCount`

`npm run redirects:catalog` (no-op until duplicate listings exist). Old
`/api/products*` endpoints untouched and still live.

**Deferred (note for later):** wishlist/cart are still keyed on a specific

### M3 — Cart + checkout  ✅ shipped

- Add-to-cart picks default offer if customer didn't explicitly select one
- Checkout locks the offer price at order time (so a seller raising the
  price after the customer added to cart doesn't surprise them)

priceAtPurchase at order time, and BLOCKS (naming the item) if a chosen offer
went unavailable — never silently swaps seller/price. In-flight legacy carts

### M4 — Seller upload flow  ✅ shipped
- Seller dashboard "Add product" → first step: search catalog by brand + name
- If match → "Add your offer" form (price + stock + sku only)
- If no match → "Create new catalog product" full form (creates BOTH the
  CatalogProduct AND the seller's first offer in one transaction)
- Existing seller products show under a new "My offers" tab

**Shipped (M4):** Search-first add-product flow. New endpoints:
`GET /api/catalog/search?q=&brand=` (seller-auth; finds catalogs incl
zero-offer ones, flags `youAlreadySell`), `POST /api/products/offers`
(add offer to an existing catalog — inherits brand-level fields, blocks a
duplicate offer per seller), and `POST /api/products/catalog` (create
CatalogProduct + first offer in a Mongo transaction). Duplicate handling =
"smart join": same brand+name → attach to the existing catalog (no dup);
same name + different brand → deterministic suffixed slug (like M1); a
second offer for a catalog you already list is blocked with a pointer to
edit. Frontend: DashboardProductNewPage is now search → add-offer / create-new;
ProductForm gained a `catalog` mode (POST /products/catalog); products page
reframed as "My offers" with a per-offer link to the shared catalog page.
listMine populates catalog. Purely additive — NO data migration; deploy
backend + frontend together.

### M5 — Admin tools  ✅ shipped
- Catalog list page (admin can edit canonical name / description / images / SEO)
- Offer audit page (per catalog, see all sellers, prices, stock)
- "Possible duplicate" detector — runs on a schedule, flags catalog products
  with very similar names for a human to merge
- Manual merge / unmerge actions

**Shipped (M5):** New `adminCatalogController` under `/api/admin/catalog`
(gated by a new `catalog` permission): list (q/brand/status + offersCount),
get-one + FULL offer audit (every offer incl. inactive / unapproved sellers),
update canonical name/description/images/sizes/mrp/SEO/status (slug stays
stable on rename so URLs never break), `GET /catalog/duplicates` detector, and
`POST /catalog/:id/merge` + `/unmerge`. Merge is REVERSIBLE: it re-points the
duplicate's offers to the survivor, ARCHIVES the duplicate (status:'archived')
with provenance (`mergedInto` + `mergedOfferIds` + mergedAt/By on
CatalogProduct), 301-redirects its slug, and recomputes pooled review ratings;
unmerge moves those offers back, reactivates it, and removes the redirect.
Detector = same-brand (or both-brandless) token-set (Jaccard ≥0.6) similarity —
cross-brand same names are NOT flagged (legitimately different products); also a
schedulable `npm run detect:duplicate-catalogs` script. Admin UI: new "Catalog"
sidebar module → list + duplicates panel (catalog/page.tsx) and edit + offer
audit + merge/unmerge (catalog/[id]/page.tsx) using RichTextEditor + MediaPicker
+ confirm dialogs.

**Deploy note:** additive — no data migration. Superadmins get catalog access
automatically; STAFF users need the new `catalog` permission granted (Staff
page). Deploy backend + admin together.

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| Migration corrupts production data | M1 ships behind a feature flag. Migration is idempotent + has a `--dry-run` mode that prints what it would do |
| Frontend reads break during cutover | M1 doesn't touch any reads. M2 reads catalog API but old product API stays alive |
| Cart in flight when M3 ships | Cart migration: existing cart items get auto-resolved to the linked catalog at the moment of next view |
| Sellers don't know how to "join" a catalog | M4 ships with a search-first UI; M5 admin can manually merge duplicates that slip through |
